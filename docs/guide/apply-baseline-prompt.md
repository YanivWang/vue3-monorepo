# 落地基线的 Prompt 模板

把 [可推广的工程化基线](./portable-baseline.md) 应用到另一个项目时，交给 AI agent 的起手 prompt。

**最少只需填两处：基线仓库路径、目标项目路径。** 其余交给 agent 自己去查——它有代码库访问权限，项目形态、已有门禁、存量债务都能查出来，比人填得准。

只有一类信息 agent 查不到，**知道就一定要补上**：那些「看不出来的坑」。典型如某个配置文件是生成产物、手改会被覆盖；某个检查历史上出过事故所以刻意保留某种写法。这类信息不写，agent 的改动会被下一次构建冲掉，或者把有意为之的设计当成缺陷"修"掉。

::: warning 立场：对齐水准，不是对齐长相
这份 prompt 刻意不叫「应用配置」。判断标准是**「这道防线在目标项目里成不成立」**，
不是「基线仓库有没有这个文件」。借鉴不了的部分要用目标项目的技术栈重新设计等效方案，
而不是跳过——所以模板里「借鉴不了的，请设计等效方案」那一节不能删。
:::

## 模板

```text
把 <目标项目> 的工程化水准，提到 <基线仓库> 那个档次。

注意这不是「让它长得像 <基线仓库>」：能借鉴的借鉴，借鉴不了的，
按目标项目的实际情况设计等效方案。判断标准是「这道防线在这个项目里成不成立」，
不是「基线仓库有没有这个文件」。

## 两个仓库

- 基线来源：<基线仓库绝对路径>
- 应用目标：<目标项目绝对路径>

先读基线仓库的 docs/guide/portable-baseline.md（按「直接抄 / 骨架能抄 / 搬不了」
分好了三档，开头有给 AI 的使用说明）和 AGENTS.md。

## 第一步：自己摸清目标项目

不要问我这些，去查，然后把结论写给我看：

- 包管理器与版本、仓库形态（单包 / monorepo）、CI 平台、私有源情况
- 现有的门禁有哪些：package.json 的 scripts、.husky/、lint-staged、CI 配置
- 现有的配置文件：tsconfig 系列、eslint、prettier、stylelint、
  .editorconfig、.vscode 是否入库
- 存量债务：类型错误数、lint 告警数、有没有基线文件、测试覆盖情况
- **哪些配置文件是生成产物**（改了会被覆盖的那种）

## 我知道但你查不到的

<只写 agent 查不出来的：历史事故、有意为之的怪写法、
 生成产物的来源、已经做过一半的事。没有就写「无」>

## 能直接借鉴的，逐项评估后落地

对照 portable-baseline.md 的第一、二节逐项过。第一节的直接抄；
第二节的只抄骨架，路径 / scope / 分层规则按目标项目重写。
每项先说目标项目现状，再说要不要动、怎么动。

## 借鉴不了的，请设计等效方案

不要因为「基线仓库的做法搬不过来」就跳过——先问这道防线在目标项目里
成不成立，成立就用目标项目的技术栈重新实现：

- **版本单点锁定**：基线仓库用 pnpm catalog 把版本收在一处。目标项目的包管理器
  有没有对等能力？覆盖不到的部分，多个包声明同一依赖的不同版本时有没有办法拦住？
- **依赖安全**：先确认目标项目的 audit 命令能不能跑通（私有源通常没有 audit 端点，
  指定官方 registry 试试）。能跑通就按同样的棘轮思路实现——按公告 ID 记基线、
  基线外的失败、critical 不允许进基线；跑不通就说明白为什么，不要硬做
- **依赖更新**：基线仓库用 dependabot。目标项目的 CI 平台侧有没有对等物
  （renovate 等），值不值得上，你判断并说明理由
- **CI 门禁**：模式是「CI 只跑一条命令、这条命令本地能跑」。检查目标项目
  是否已是这个形态、有没有漏项、CI 配置本身是不是生成产物
- **供应链与项目独有约束**：目标项目可能有基线仓库没有的约束（私有源白名单、
  单例校验、产物同步等）。找出来，用同一套标准判断它们是否成立、是否活着

## 目标项目自己的问题也一并看

目标项目通常有基线仓库没有的检查脚本和存量债务。用同一套标准审一遍：
这些检查是不是活的、失败时会不会表现为「通过」、有没有反例验证过。
发现问题按同样的原则修——不要只做单向对齐。

## 工作方式

- 从根因修，不要打补丁。看到症状先找机制，修机制
- 每加一道门禁，必须实测它会红：构造应当被拦的输入，确认命令非零退出，再还原
- 每步改完跑目标项目的全量门禁命令，确认存量基线没涨
- 抄机制不抄数字：阈值、printWidth、Node 版本都按目标项目实际情况定
- 在当前分支提交，不要新建分支。提交信息写清楚「为什么」，不只是「改了什么」
- 分阶段提交，不要把纯格式化重排和实质改动混在一个提交里

先只做调研和测量：每一项的现状、影响面、建议方案，以及借鉴不了的那些
你打算怎么做。列出来给我确认后再动手。
```

## 为什么模板长这样

几处刻意的设计，改模板时别顺手删掉：

**让 agent 自查现状，而不是人来填。** 项目形态、已有门禁、存量债务都是可查的，人填反而容易漏或过时。人只需要补 agent 查不到的那一类——历史事故、有意为之的怪写法、生成产物的来源。分工错了，要么人写一堆废话，要么 agent 在错误前提上动手。

**「借鉴不了的」是开放问题，不是排除项。** 直接写「pnpm catalog 用不了」会让 agent 跳过；写成「yarn 1 的 resolutions 能覆盖到什么程度？」才会得到方案。防线成不成立与实现手段能不能搬，是两个问题。

**「目标项目自己的问题也一并看」。** 目标项目通常有基线仓库没有的检查脚本和存量债务。只做单向对齐会漏掉它们——而这些往往才是最需要审的部分，因为没人拿标准量过。

**结尾要求先调研后动手。** 类型感知 lint 这类改动，在存量大的项目里可能炸出几百条错误，方案（清零 / 棘轮 / 缩作用域）取决于实际数字。先出数字再定方案，比先动手再回滚省事。

**「实测它会红」是硬要求。** 没做过反例验证的门禁只能算配置——最贵的洞不是报错的门禁，是失败时表现为「通过」的门禁。
