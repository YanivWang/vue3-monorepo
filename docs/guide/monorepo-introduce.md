# Monorepo 现代化工程管理方案

**Monorepo**（单仓多包）是把多个应用与共享库放在**同一个 Git 仓库**里，用 **pnpm workspace**（或同类工具）统一安装、构建与发布边界的做法。它不是什么新概念，但在中大型前端团队里已成为一种**默认的工程形态**：用一套仓库把「规范、工具链、可复用代码」绑在一起，降低协作与演进的摩擦。

本页说明 **为什么** 值得采用 Monorepo、**能带来哪些好处**；日常怎么执行 `filter`、加依赖、代码放哪等**具体操作**，见 [pnpm workspace 日常操作](./monorepo-workflow.md)。

## 为什么要用 Monorepo

在多应用、多端（例如本仓的 PC 管理端与 H5）并存时，常见的反模式是：

- 多个独立仓库复制同一份 ESLint、TSConfig、请求封装与工具函数；
- 版本升级时各仓进度不一，行为差异难以发现；
- 共享逻辑只能发包到私有 npm，迭代链路长，或干脆 copy-paste。

Monorepo 用**一个事实来源（single source of truth）** 解决上述问题：**规范与依赖策略在根目录统一**，业务包通过 **workspace 协议**直接引用本地包，改一处即可被多端消费。

## 核心优点与好处

### 1. 规范与工具链的统一化管理

- **一份配置，全仓生效**：ESLint、Prettier、Stylelint、TypeScript 基座、Vitest 等可以集中在根或基座包，子应用**扩展而非重写**。
- **CI 与脚本口径一致**：根 `package.json` 封装 `typecheck`、`lint`、按包过滤的构建命令，减少「在我机器上能过、在 CI 却不过」的差异。
- **升级成本可控**：依赖版本可通过 catalog / 根约束统一抬升，避免各应用各自锁死老版本。

对本仓而言，这些内容在 [代码质量与规范约束](./quality-gates.md)、[环境与命令速查](./getting-started.md) 中有具体落地。

### 2. 代码与领域的统一化管理

- **边界清晰**：应用（`apps/*`）负责路由、页面与端侧装配；共享能力进 `packages/*`，通过 `exports` 明确**对外 API**，避免深层路径依赖。
- **原子改动**：一次 PR 可以同时改「共享库 + 调用方」，类型检查与测试能在同一变更集里完成，减少「先发包再等各端升级」的接力。
- **可见性强**：相关代码在同一 diff、同一 Code Review 里，架构腐化更容易被看见。

本仓的目录哲学见 [项目与目录约定](./project-conventions.md)。

### 3. 方便的代码共享与复用

- **零发包成本的内部依赖**：`workspace:*` 引用本地包，改完即时被 admin / h5 消费，适合高频迭代的工具、类型、请求内核与业务无关的 hooks。
- **按需导出**：通过 `package.json#exports` 控制可引用表面，避免「能 import 就能用」导致的隐性耦合。
- **多端复用而不混淆 UI**：例如请求核心与 PC/H5 的 UI 反馈分层（本仓的 **`@vue3-monorepo/request-core`** 与 **`@vue3-monorepo/shared/request-pc`** / **`@vue3-monorepo/shared/request-h5`** 即是一例），共享逻辑与端差异化可以并存。

更细的「新代码放哪、怎么加依赖」见 [pnpm workspace 日常操作](./monorepo-workflow.md)。

### 4. 协作与工程效率上的附加收益

- **新人 onboarding 一条路径**：克隆一个仓库即可完成环境安装与多应用试跑，文档与约定也集中在一套体系里（见 [新手上路](./onboarding.md)、[文档体系总览](./doc-system.md)）。
- **大规模重构更可执行**：重命名、迁移目录、调整 exports 时，可在仓库内**全局搜索与批量替换**，配套类型检查一次拉齐。
- **工具与脚手架共建**：例如本仓的「一键新增业务应用」可在统一约束下生成新包（见 [脚手架一键新增业务应用](./adding-a-new-app.md)），避免各业务线各自拷贝模板。

## 需要接受的代价（诚实边界）

Monorepo 不是「只有优点」：

- **仓库体积与克隆时间**会随历史增长；通常用稀疏检出、CI 缓存、**受影响子集构建**（filter / turbo 等）缓解。
- **权限与可见性**若需「按目录细粒度隔离」，要依赖宿主平台能力；纯 Git 层面是整仓可见。
- **发布节奏**若为「多包独立版本」，需要清晰的 changeset 或发布流程（本仓若以应用部署为主，则多数场景是随应用发版）。

是否采用 Monorepo，本质是**用仓库边界换统一治理**；对多应用、强共享的前端组织，收益往往大于成本。
